# NetRedirector v1.9.1

## 語音打洞、DNS 洩漏、IPv6 子網，以及給自家工具的本機控制 API

這一版四件事，前三件都是**不會報錯、也不會中斷**的問題 —— 出事了只會「安靜地不動作」，
所以都不容易自己發現。

最嚴重的是第一件：**UDP relay 會在背景無聲失效**，而且失效之後不會自己好，
只能把整個程式關掉再開。它的表現是「Discord 語音偶爾打不通」，但根因跟 Discord 無關，
所有走 UDP 的流量都會掉進同一個洞。

---

## 一、修正：UDP relay 的連線會無聲失效，而且永不重建

### 症狀

用代理時 Discord 語音（WebRTC）**打洞失敗**，換版本有時好有時壞。同一時間：

- 把 Discord 的規則改成直連 → 打洞正常；
- 繞過引擎、直接對代理做 UDP ASSOCIATE → 也正常；
- 只有「經引擎的 UDP relay」這條路 **0/4 全滅**，連 DNS over UDP 都 timeout。

把 NetRedirector 整個關掉再開，立刻恢復 4/4。這個「重開就好」是最關鍵的線索。

### 根因：代理端的 relay 埠死了，但引擎不知道

SOCKS5 的 UDP 是「一條 TCP 控制連線 + 代理端配一個 relay 埠」。那個 relay 埠的壽命
取決於**代理後面的 NAT 對應**：手機熱點換基地台、或電信商的 UDP NAT 項過期，都會讓它
**靜默停止轉發**，而 TCP 控制連線靠 keepalive 還掛著 ESTABLISHED。

於是引擎這邊看到的是：

- `select()` 永遠等不到 EOF（控制連線還活著）；
- `sendto()` 永遠不會失敗（UDP 無連接，送到死埠不會報錯）；
- 所以既有的「連續送出失敗就重建」機制永遠不會觸發。

實測到的那一筆：引擎在 **17:04 建立的 association，到隔天 09:11 還在被使用**，
中間十幾個小時的每一個 datagram 都送進黑洞。

> 這也是為什麼「1.8.5 之前好像沒事」：那時候 UDP 歸因失敗會直接走直連，
> **根本沒進 relay**。1.8.5 修好歸因之後，流量第一次真的走進這條路，
> 才撞上這個一直都在的老問題。

### 修正：用「沉默」當判據，而不是等錯誤

唯一觀察得到的訊號是**沒有回程**。所以 association 現在會記錄「最後一次收到回程的時間」
與「自那之後送出的 datagram 數」，超過門檻就丟掉它；下一個 datagram 會重新 dial，
跟既有的 sendto 失敗路徑完全一樣。

門檻分兩種，因為「從來沒回過」跟「曾經回過」的意義不同：

| 狀態 | 條件 |
| :--- | :--- |
| 曾經收到回程（雙向流量） | 送出 20 個 datagram 且沉默超過 15 秒 |
| 從未收到回程（單向流量） | 送出 200 個 datagram 且沉默超過 60 秒 |

第二列是刻意放寬的：syslog、單向心跳這類流量本來就不會有回程，
用 15 秒的門檻會讓它們每 15 秒被重新 dial 一次，純粹是浪費。

> 刻意**沒有**用「閒置超時」當唯一判據 —— Discord RTC 有持續流量，
> idle 永遠不會觸發，那正是它能在黑洞裡活 16 小時的原因。

計時用 `GetTickCount()`，因此也處理了 49.7 天環繞。

## 二、修正：DNS 查不到來源行程時，不再偷偷走直連

### 症狀

在「代理 + 一條萬用（`*`）規則」這種最常見的設定下，**大部分 DNS 查詢走代理，
但有一部分的查詢會走直連** —— 而且是明文送出。畫面上、日誌裡都不會有任何異常。

### 根因：同一個設定，兩種結果

引擎對每一條流量都要先問「這是哪個行程發的」。問不到的時候（`pid == 0`），
過去的行為是**無條件走「未知行程」的處置**（預設是直連）。

但 DNS 的處置其實**不該取決於「問不問得到行程」**：引擎另外有一個設定
「DNS 走代理」（`dns_via_proxy`，預設開）。於是同一台機器上會同時存在：

- 歸因**成功**的 DNS → 進規則 → 有萬用規則 → **走代理**；
- 歸因**失敗**的 DNS → 在進規則之前就被攔下 → **走直連**。

兩者用的是同一個設定，結果卻相反，而「漏掉的那一半」在日誌上跟正常流量長得一樣。

歸因失敗對 UDP 而言是常態（UDP 沒有 `TIME_WAIT`、沒有握手，socket 常常在引擎查表
之前就關掉了 —— Windows 的 DNS Client 是慣犯），所以這不是罕見路徑。

### 修正

`pid == 0` 且目的埠是 53 時，改成**與「查得到 pid 但查不到名稱」同一條路**：
帶著**空的行程名**繼續進規則比對。

- 萬用（`*`）、PID、域名規則照樣能匹配；
- 指名行程的規則自然不匹配（空名字不可能等於某個行程名）；
- 若沒有規則匹配，規則引擎本來就會回直連 —— 最壞情況與過去完全相同。

同時**維持對稱**：`dns_via_proxy` 關閉時，不論歸因成功或失敗，DNS 一律直連
（這個偏好優先於任何規則）。這條對稱是刻意保證的，否則就會出現
「一半 DNS 明文外洩」這種看不出來的洩漏。

另外把 `pid == 0` 時的「防迴圈」判斷（跳過自己行程）移進正確的分支 ——
`g_current_process_id` 在尚未初始化時是 0，原本會把 `pid == 0` 誤判成「自己」。

## 三、新增：IPv6 CIDR 子網規則（例 `2001:db8::/32`）

### 症狀

IPv6 的規則只能填**完整位址**。想擋或想導一個子網，例如「所有
`2001:4860::/32` 的流量走代理」，規則欄位填 `2001:4860::/32` 會**完全沒有效果，
也不會有任何提示** —— 它被當成一個字串去比對，永遠不會等於任何一個位址。

一個 /64 有 2⁶⁴ 個位址，所以「列出整個子網」不是選項：這個缺口等於
**IPv6 的規則功能實際上只有一半**。

### 修正

規則的 hosts 欄位現在支援 IPv6 的 CIDR 表示法：

```
2001:db8::/32      整個 /32 子網
::/0               全部 IPv6（等同 IPv6 的萬用字元）
2001:db8::/128     單一位址（與直接寫位址等價）
```

格式錯誤（前綴不是數字、超過 128、位址部分不合法）一律**視為不匹配**，
不會退化成字串比對 —— 否則打錯字會變成一條**永遠不匹配卻毫無提示**的規則。

設定介面的 hosts 提示文字也一併加上範例。

### 順帶修掉的一個無聲缺陷

「這個欄位裡有沒有域名」的判斷過去用的是 `is_ip_like_pattern()`，而它問的其實是
**「是不是點分 IPv4」**。於是任何含 `:` 或 `/` 的字串（IPv6 位址、以及新的 CIDR）
都被當成**域名**，每次新增或編輯這類規則就會多觸發**一次全機 DNS 解析快取清除**
外加兩次註定失敗的解析。既有的 IPv6 精確位址規則本來就會踩到，CIDR 只是讓它變常見。
現在改用專門的判斷（含 `:` 或 `/` 就是位址，不可能是主機名）。

> ⚠️ 已知限制：**IPv4 的 CIDR（例如 `10.0.0.0/8`）仍然是陷阱** —— IPv4 分支還沒有
> 同樣的處理，它會被當成域名解析、必然失敗、規則靜默永不匹配。要動 IPv4 CIDR 時
> 會連這條一起處理。

## 四、新增：本機控制 API，以及「自動偵測並加入直連程式」

### 為什麼需要

同一台機器上如果有我們自己維護的工具（例如 MultiSocksDownloader），它必須
**直連**才能自己掌握通往各個 SOCKS5 代理的連線；一旦它的連線被 NetRedirector
再轉一次，多代理聚合就整個失效。

過去的解法是使用者手動去規則頁加一條 DIRECT。現在多了一個選擇：

- **自動**：齒輪選單的「自動偵測並加入直連程式」。啟動時掃描一次，
  清單裡的程式若正在執行、而且使用者還沒為它建過任何規則，就補上一條直連規則。
  預設清單只有 `MultiSocksDownloader.exe`。
- **被動**：本機 HTTP API，讓工具自己開口要求。

```
GET  /ping                           回傳版本與執行狀態
GET  /rules[?target=NAME]            查詢規則（可依行程名過濾）
POST /ensure-direct {"target": "x"}  確保該行程名有啟用中的 DIRECT 規則
```

### 幾個刻意的設計

- **只綁 `127.0.0.1`，且要 token**。只綁 loopback 擋掉了遠端，但同機的其他行程
  還是連得進來，所以請求要帶一個共享 token（放在使用者家目錄，
  呼叫端讀同一個檔案即可）。
- **不用具名管道，用 loopback TCP**。NetRedirector 必須以管理員身分執行，
  呼叫端卻通常是一般權限；具名管道受完整性等級 ACL 限制，管理員行程開的管道
  一般權限常被拒絕，loopback TCP 不受此限制。
- **`/ensure-direct` 是冪等的**。C 核心的 `AddRule` 不去重，重複呼叫會堆出多條
  相同規則，所以已有啟用中的 DIRECT 名稱規則時直接回報，不新增。
- **尊重使用者的停用意圖**。啟動掃描只看「該行程正在執行」且「使用者尚未為它
  建立任何規則（含停用）」，所以你把自動加的規則停用或刪掉之後，它不會每次啟動
  又長回來。
- **規則的 `auto` 標記會存進設定檔**，這樣使用者刪除時才能一併把它移出清單。

> ⚠️ 把 `python.exe` 這類**通用直譯器**設成直連，會讓**所有** Python 程式一起直連
> （包含 NetRedirector 自己如果也是 Python 跑的話）。API 仍允許，但會在日誌留一筆提示。

## 實機端到端驗證

C 測試只證明「比對與決策邏輯」，證明不了「實機真的改道」。這次做了
新舊 DLL 的配對量測（儀器是自製 SOCKS5 代理，記錄引擎實際交出去的東西）：

| 項目 | 舊版 | 新版 |
| :--- | :--- | :--- |
| IPv6 CIDR 規則 `2001:4860::/32` | `Direct (TCP)`，代理零記錄 | `Proxy (TCP)`，代理收到 `ATYP_IPV6` |
| 不涵蓋的 CIDR `2001:db9::/32` | `Direct (TCP)` | `Direct (TCP)`（對照組） |
| 歸因失敗的 DNS（`dns_via_proxy` 開） | **未被代理收到**（洩漏） | **被代理收到** |
| 歸因失敗的 DNS（`dns_via_proxy` 關） | 未被代理收到 | 未被代理收到（偏好優先） |

UDP relay 那一項沒辦法用同一個儀器量，因為要復現的是「代理端的 relay 埠在背後死掉」。
這次的作法是**先復現、再確認假設**：

| 組 | 路徑 | 結果 |
| :--- | :--- | :--- |
| A | 直連（DIRECT 規則） | 4/4 STUN，來源正確，映射一致 |
| B | 經引擎 relay | **0/4**，DNS over UDP 也 timeout |
| C | 繞過引擎直連代理 | 2/2 STUN，映射一致 |

B 全滅而 A、C 都正常 ⇒ 問題在引擎的 relay，不在代理也不在網路。接著查到
「同一條控制連線已存活 16 小時」，把程式重啟（清空 association、拿到新的 relay 埠）
之後探針立刻回到 4/4、映射也換成新埠 ⇒ 老化假設成立。修復後的門檻行為由那 13 項
單元測試釘住。

> 歸因失敗的 UDP 流量無法「隨手製造」—— 引擎有一層 socket 事件快取會先回答。
> 這次是用**壓力測試**逼出來的：灌爆引擎的 socket 事件佇列（它自己就設計成
> 「寧可丟事件也不要長大」），讓快取答不出來，再送 DNS 查詢。方法與腳本
> 在 `.workbuddy-ai/ab/`（`run_191_ab.py`、`run_flood_ab.py`）。

## 升級方式

使用內建自動更新即可。若更新流程本身有問題，直接下載本頁 zip 手動覆蓋
（`NetRedirector.dll` 必須與執行檔同目錄）。

> 提醒：設定檔 `config.json` 放在程式目錄。**手動換版本時請不要把整個資料夾
> 直接刪掉重解壓**，否則設定會跟著消失；內建自動更新會自動保留它。
